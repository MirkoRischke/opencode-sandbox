## Native GROUP/HEAD semantics matter for fresh-only preparation

`fresh-head.log` uses **two different newly created prep VMs**, destroys both before restoring children, and records:

```text
CREATE fresh1 ... Reason:initialized Changed:true parent=<nil>
CREATE fresh2 ... Reason:diverged Changed:false parent=<nil>
FRESH_CAPTURE_DOES_NOT_AUTO_ADVANCE_HEAD confirmed
EXPLICIT_SELECT ... Reason:selected Changed:true
FAILED_CAPTURE_PRESERVES_SELECTED_HEAD PASS
REAL_GIT_WORKTREE a "generation-2\na"
REAL_GIT_WORKTREE b "generation-2\nb"
```

Same-prep successive captures in the Docker harness automatically fast-forward, but that is **not** the approved fresh-only refresh workflow. Required native sequence: create uniquely named generation, check success, then `Snapshot.GroupHead(ctx, group+":"+generation)`. Launch can use `Snapshot.Get(ctx, group)` / `RestoreSandbox(ctx, group, ...)`; no launcher-maintained JSON mapping needed. Create and select are two operations: interrupted selection leaves old HEAD, with an unpublished generation available natively. Not an atomic combined transaction; concurrent refresh ordering was not tested.

Removal: native rejects deleting current HEAD while other members exist **even with force**. Old members with indexed descendants require force. Removing old members first and then the last/current member succeeded, clearing HEAD; already restored disks remain independent. Snapshot removal command must account for that ordering, not blindly remove HEAD first.

## Restore enrichment, TLS and credentials

1. Restore accepts policy/mount/resource overrides, **not create-time secrets, labels, workdir, TLS configuration, upstream proxy configuration, or arbitrary environment**. `ConnectOrCreateSandbox` creation options explicitly do not update an existing restored VM. Capturing prep credentials is neither necessary nor acceptable.
2. Supported partial workaround tested: restore boots; stop it **before project commands**; Modify labels/workdir/secrets with next-start; start detached; ensure Docker. First secret addition cannot apply live (`secret EXPERIMENT_TOKEN requires restart`) and implicitly enables default TLS interception. Later host/value updates can apply live. This costs another boot and requires fail-closed cleanup before exposing the VM.
3. **Blocking safety mismatch:** Go `SecretModifySpec` lacks selected-header substitution. The core supports it and Rust modification builder exposes it, but Go's public wire shape does not. Default substitution enables all headers. Do not ship this workaround for the current configured `headers` contract; do not silently broaden it or send raw credentials into guests. Minimum prerequisite is a supported API exposing that field (or approved narrowly scoped native binding); no upgrade or workaround implemented here. Until then, a **secret-free** snapshot restore is the minimal viable path, not a claimed full launcher replacement.
4. Controlled endpoint: host loopback on one ephemeral high TCP port, private throwaway CA, host alias SAN. Prep intercepts this port and verifies upstream with explicit CA. Restore's subsequent secret addition intercepts default **443**, not that custom port; endpoint receives unchanged placeholders, despite admission working for A. Earlier default-CA run fails certificate validation without explicit endpoint trust (`curl` exit 60), confirming those custom trust/interception choices were not restored. No `curl -k`, disabled upstream verification, broad host grant, or secret release over plaintext.
5. **CA transition actually tested:** final prep uses its own throwaway interception CA; after child enrichment/reboot, `/.msb/tls/ca.pem` changes to destination runtime CA in both children. Normal verified HTTPS echo then succeeds. However **old prep CA remains in captured system trust bundle**. Agentd appends current trust; this is not old-root revocation. Old CA retention also explains why final controlled direct-TLS request succeeds without special curl trust. A clean template must not embed a credential-bearing/custom trust setup that one expects restore to erase. Host default CA files were never rotated/edited.
6. Upstream proxy configuration and custom corporate CA migration were **source-reviewed only**, not exercised. Public restore/Go Modify cannot install arbitrary replacement TLS/proxy settings. Container-specific CA stores are also untested; guest agent trust installation does not imply nested containers trust it.

## Limits, cleanup and leftovers

- Tiny `hello-world` baseline only; not a representative large Docker cache, BuildKit/Compose workload, image GC, performance benchmark, or proof of physical storage savings. Restore latency excludes Docker readiness and enrichment. Negative network checks cover representative targets, not every protected range.
- Two initial harness-only TLS problems: using a CA certificate directly as server leaf (fixed by signed leaf), and PKCS#1 custom CA key not accepted by runtime (fixed by PKCS#8). Secondary 64 MiB root failed ext4 formatting; 256 MiB succeeded. No tool upgrades/builds used to fix these.
- Final `msb sandbox ls`: original six user VMs with original running/stopped states; **zero experiment VMs**. `msb snapshot list`: **No snapshots indexed**. Existing images untouched; no host Docker containers created.
- Native member removal leaves **empty group metadata directories**, deliberately not manually removed from runtime storage: `rsexp-1792323502-repo-83d3e04f`, `rsexp-1792323695-repo-83d3e04f`, `rsexp-1792323782-repo-83d3e04f`, `rsexp-docker-repo-006b2107`, `rsexp-repo-006b2107`. No public group-delete command found. Temporary harness/fixture/log directory ~396 KiB (before private-key removal), retained for reproduction.
- Approved product design remains unchanged: fresh prep only; explicit create/remove; baseline restore for a new worktree or fresh fallback; no migration/automatic outdating. Prep command in a mounted worktree can modify host files. None of these production commands were implemented.
