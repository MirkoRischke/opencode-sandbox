# Where to start Docker Engine in Microsandbox VMs

**Recommendation: keep Docker's configuration and lifecycle script in the image; invoke an idempotent `ensure-started` operation from Go `Prepare`, immediately after connecting/creating/starting the VM and before project initialization. Do not rely on Dockerfile `ENTRYPOINT`/`CMD` to start it.** In pinned Microsandbox **0.7.8**, SDK creation is boot-only; OCI defaults are executed only by an explicit default-workload execution call. This is a verified SDK/runtime distinction, not Docker-container lifecycle intuition. Add a corresponding explicit Docker shutdown operation **before** VM `Stop` if clean Docker/container shutdown matters. [M1–M8, R1]

## Verified Microsandbox lifecycle

| Path | What actually happens in 0.7.8 | Docker consequence |
| --- | --- | --- |
| New sandbox | Go dispatches creation through native FFI to Rust. Local creation boots the VM and waits for the agent relay readiness handshake; it does not invoke an image workload. [M1–M3] | `ENTRYPOINT ["dockerd"]` alone does nothing in this launcher. Agent-ready is not Docker-ready. |
| Existing running sandbox | `connect_or_create` uses the persisted identity/configuration and connects; it does not reboot or run OCI defaults. [M1, M4] | Ensure operation must recognize a healthy existing daemon and avoid spawning another. |
| Existing stopped sandbox | Same operation starts the persisted sandbox in detached mode; local start loads saved configuration/rootfs state and calls the same boot/agent-readiness implementation. [M4, M5] | This is a **cold start using persistent disk**, not RAM/process resume. Start Docker again; cached images/data may remain, running processes do not. |
| New image / new create options | Options are used only for creation; existing sandboxes retain saved configuration and pinned rootfs state. [M1, M4, M5] | Rebuilding `opencode-sandbox:poc` does not establish that old VMs contain Docker or the new script. Fail clearly and require a deliberate recreate/migration; do not silently delete persistent disk. |
| Literal exec | `ExecStream("bash", ...)` executes that literal program; OCI entrypoint/CMD do not wrap it. Explicit `ExecDefault*` resolves stored entrypoint + CMD and sends an ordinary exec request. [M6] | A Docker entrypoint cannot intercept the existing initialization or interactive `AttachWith("opencode", ...)`. |
| Default PID 1 | Microsandbox agent is PID 1. Full init requires explicit init handoff (`WithInit`), plus an image containing the chosen init. `ENTRYPOINT` and guest init are different concepts. [M7] | Debian package/service installation or `systemctl enable docker` alone does not make systemd run at boot. |
| Detached | Detached VM process lifetime is independent of creator exit after successful startup. This is VM process ownership, not a service manager for guest daemons. [M3–M5, M9] | No automatic Docker restart-on-crash, readiness, or graceful Docker stop is provided. |

### Important source/documentation inconsistency: `Close`

Go's `Sandbox.Close` comment says a `WithDetached` sandbox is stopped by `Close`, and recommends `Detach`. However, the **actual pinned local implementation** calls `finish_detached_creation` on successful detached create/start; that method takes the process handle out of local state and disarms it. Native `msb_sandbox_close` only drops the SDK object, stopping a VM only if that object still owns lifecycle. Connected handles also do not own VM lifecycle. Thus for the successfully detached local paths used here, source supports the repository's connection-only `Close` interpretation; the Go comment is stale/inconsistent. Do not use `Close` as Docker/VM cleanup; this repository already explicitly calls `Stop`. Confirm the loaded native runtime matches the pin in acceptance testing. [M3, M5, M9]

## Will a daemon survive `ExecStream` completion?

**Yes, a deliberately detached, redirected descendant is source-supported; a bare shell `dockerd &` is not a sufficient lifecycle design.** Distinguish three events:

1. **Exec handle close:** Go `ExecHandle.Close` and native `msb_exec_close` release the handle without signaling the process. `ExecStream` context controls the start handshake, while `Recv` cancellation ends a wait. A configured exec timeout is different: it sends `SIGKILL`. [M8]
2. **Shell exit / stream completion:** pipe-mode exec uses `setsid` to create a session/process group. Its reader drains stdout/stderr **until EOF before reporting exit**. A background daemon inheriting those pipes can prevent `ExecEventDone`, so this repo's `Exec` never returns. Redirect daemon stdin from `/dev/null` and stdout/stderr to a guest log; detach it from the startup command's process group/session if independence is intended. Dropping the guest `ExecSession` releases registration, not the descendant process. These source facts support survival after a correctly completed startup exec, but they are not an executed `dockerd` integration result. [M10, M11]
3. **SDK connection disappearance:** agent relay-client cleanup sends `SIGKILL` to active exec process groups owned by that connection. Consequently “exec-handle close does not kill” does **not** mean “all running exec commands survive SDK disconnect.” A completed, fully redirected startup session is removed; an independently session-detached daemon should not depend on that transport ownership. Validate these exact boundaries rather than trusting `nohup` alone; `nohup` does not escape process-group `SIGKILL`. [M10–M12]

`dockerd` itself runs in the foreground and logs to its inherited output by default. An image-owned launcher can background/session-detach it and then perform readiness checks. Docker normally manages a private `containerd` if none is configured/running; do not copy a systemd unit's `-H fd://` or explicit system-containerd socket into a no-systemd startup script. Unix socket activation requires systemd-provided descriptors; an absent externally managed containerd is another avoidable startup failure. [D2, D3]

## Proposed ownership contract (design, not implementation)

**Image owns Linux/Docker details; Go owns when initialization is required and whether launch succeeds.** Suggested shape is one image-owned script with `ensure-started` and `stop` operations; names/paths are not prescribed.

### On every `Prepare`

1. After successful connect/create/start and installation of the existing failure-cleanup defer, invoke the image-owned ensure operation **before** GitHub/mise/project startup. This covers first create, cold restart, and reconnect. Do not spread Docker shell flags, PID handling, or package installation across Go. [R1; design inference from M1–M6]
2. Serialize startup if multiple launchers may connect concurrently. Check the **guest-local** Engine API, not just PID/socket existence. Return success for an already healthy daemon; if another daemon is still starting, wait within a bound instead of racing another launch. Keep a missing script/binary and invalid daemon configuration as explicit failures. [M4, D2; design recommendation]
3. Start as guest root (current image has no `USER` override). Use only `unix:///var/run/docker.sock`; no host socket mount, TCP Engine listener, or Microsandbox published ports. Ensure readiness commands select that socket explicitly so inherited `DOCKER_HOST`/Docker contexts cannot test some other daemon. Do not duplicate `hosts` in both CLI flags and `daemon.json`: Docker rejects duplicate options even when values agree. [R1, D2]
4. Wait for a successful **server** request such as `docker --host unix:///var/run/docker.sock info`, with an overall startup deadline and bounded individual probes. Socket creation alone is insufficient: Moby creates listeners before daemon/BuildKit initialization and serves the API after initialization. Also detect the newly launched daemon's early death and return a useful, bounded guest-log excerpt. A successful fork is not readiness. [D4, D5; polling/failure policy is recommendation]
5. On failure, terminate/reap only a daemon this operation actually started, then return nonzero. Go should wrap the startup error and let `Prepare`'s existing cleanup stop the VM. Never delete Docker's persistent data to repair a startup error automatically. If clean failure cleanup matters, stop Docker before that VM cleanup too. [R1, D2; recommendation]

This is **startup management, not ongoing supervision**. If the daemon dies later, project commands fail until the next ensure operation. Automatic restart during the interactive session is a separate requirement: use a real guest supervisor/init if requested, or retain and monitor a foreground daemon exec using a dedicated API instead of the current synchronous `Sandbox.Exec`. The current helper waits for `ExecEventDone`, so foreground `dockerd` through it would block `Prepare` indefinitely. [R1, M8; design inference]

### On normal exit / initialization failure

**Do not assume `s.vm.Stop()` gives Docker its full graceful shutdown budget.** Agent shutdown sends `SIGTERM` to tracked sessions, then in default PID-1 mode calls filesystem teardown and poweroff. Teardown synchronizes filesystems and then sends **`SIGKILL` to all remaining processes**, with a one-second overall teardown budget. There is no Docker-specific wait; a daemon detached from its original exec session may receive no initial session `SIGTERM` at all. Filesystem flushing is not application/container shutdown. [M13]

For clean shutdown, invoke the image-owned `stop` operation **while the VM/agent still runs**, signal the verified Docker daemon with `SIGTERM`, and wait for actual daemon exit before VM `Stop`. Docker's signal trap initiates cleanup on the first SIGTERM/SIGINT; its documented daemon shutdown timeout defaults to 15 seconds. Coordinate that time with container stop timeouts, managed containerd cleanup, and the launcher's current 30-second independent cleanup context. Bound cleanup and preserve/report errors; still attempt VM stop if Docker stop fails. A PID file alone must not authorize signaling an unrelated reused PID. [D2, D4, D6, R1; lifecycle recommendation]

The SDK's `Stop` wait has no built-in deadline; its context/`WithStopTimeout` bounds observation without promising force-kill. Separately, the runtime has a normal guest shutdown-flush constant of two seconds for some termination paths. Increasing Go's wait timeout cannot add a Docker wait to agentd's immediate PID-1 teardown. VM crashes, host failure, or force-kill remain abrupt shutdown cases. [M13, M14]

## Alternatives compared

| Alternative | Assessment |
| --- | --- |
| Dockerfile `ENTRYPOINT`/`CMD` only | **Reject for this launcher.** SDK boot/create/start/connect never auto-execute those defaults. No readiness/failure integration. [M1–M7] |
| Entry point plus Go `ExecDefault*` every `Prepare` | Technically works if the default workload is itself an idempotent startup script, with correct process detachment/readiness. But the Go call is still required, and a generic OCI default-workload contract hides a specific service lifecycle operation. Prefer explicit script invocation. No built-in supervision is gained. [M6, M8; design judgment] |
| Go invokes image-owned startup/shutdown script | **Best fit now.** Small explicit integration point, covers persistent VM restart/reconnect, retains existing minimal agent PID 1, can fail launch clearly. Must explicitly design readiness, logs, detachment, and shutdown; plain `dockerd &` is insufficient. [R1, M1–M14; design judgment] |
| Full guest init + Docker service | Valid alternative if automatic boot, supervision/restart, and service-ordered shutdown are desired. Install a suitable init/image, explicitly request `WithInit`, configure its Docker service, and retain a Go readiness check. Init handoff changes the VM boot/shutdown architecture and saved configuration, not just the Dockerfile command. Not necessary merely to make Docker available for this launcher. [M7, M13; design judgment] |

## Uncertainties and required later experiments

No claim that Docker is already functional on this exact guest kernel/root-disk layout. Source settles **where startup is triggered**, not all Engine compatibility questions. Before accepting implementation, use disposable test VMs for:

- Fresh create; already-running reconnect (one daemon); stopped persistent VM cold start (new daemon, preserved image/volume data); repeated ensure; concurrent ensure if supported. Verify rebuilt-image behavior versus an old persistent VM. [M1–M5]
- Verify `/proc/1/comm`, actual cgroup availability/driver, namespaces, firewall/NAT and DNS, and Docker's selected storage backend on the managed root. Agentd default security profile preserves exec privileges while its optional restricted profile drops mount-admin capabilities; neither that nor Debian support is a runtime proof of nested containers/builds. Do not work around failures with blanket privileged flags, host sockets, or host-port forwarding. [M7, M10, D1, D2]
- After startup exec reports done and its handle closes, run another exec to prove Engine survival. Then test SDK disconnect/reconnect separately; transport loss while startup is still active; launcher termination; and normal VM shutdown. A harmless disposable background process can isolate process-lifetime semantics before testing Docker. [M8–M13]
- Run an actual container, a Buildx build and Compose project entirely in the guest; test pulls and build networking under existing Microsandbox network/TLS policy. `docker info`, `docker buildx version`, and `docker compose version` alone do not prove those workloads work. Do not disable TLS verification to make intercepted registry/build traffic succeed. [D1, D2; proposed tests]
- Inject invalid config, missing binary/script, daemon early exit, timeout, and stale runtime files; verify `Prepare` fails with actionable logs and no orphan VM/daemon. Test graceful shutdown with a container that records SIGTERM; verify Docker exits **before** VM stop, and retained data survives reboot. [M10–M14, D4–D6]
